## 2. 决议清单

### DR-01 握手构造路线（**阻塞 T-07**）

- **我的提案**：自定 spec —— `X25519 ECDH + HKDF-SHA256 + ChaCha20-Poly1305`，全部使用 mbedtls 既有原语，组合方式写成字节级规范并附测试向量。
- **理由**：PBR 帧上限 2048B 且串口逐字节流，套 TLS/DTLS 会造成记录分片嵌套，与现有 PBR1 帧语义重叠；Noise 需在两端各引入新库。自定 spec 工程量最小，且 f-day1 允许「D 提交、F 审核」。
- **需你决定**：这个组合是否「可审」。我会按以下六项交付，请确认这六项就是你的审核口径：
  1. 算法套件与库版本
  2. **KDF 标签与派生树**（`pbr_hs_` / `pbr_i2b` / `pbr_b2i` 的精确字节串）
  3. nonce 编码（字段顺序、字节序、位宽、上限后的处理）
  4. AAD 覆盖范围（哪些字段、明文还是长度前缀）
  5. transcript 的 hash 覆盖范围（握手每条消息的拼接顺序）
  6. 测试向量（正向 + 篡改/重放/降级反向）
- **若不批的回退**：退化到 Noise IK（需 D/L 确认 ESP32 侧可用实现），工期增加。
- **阻塞影响**：未决 → T-07 不开工 → T-08 / T-12 无安全前提。

### DR-02 AEAD 在 PBR1 中的装法

- **我的提案**：**帧头不动**，`payload` 换成信封 `[env_ver:1][key_id:1][nonce:12][ciphertext:N][tag:16]`；认证后 payload 必须带信封头，否则整帧丢弃。
- **理由**：两端 parser 完全复用（含噪声重同步、深度限制、超时），改动集中在 `pbr_send_frame` 与 Pi 解码后处理；只有一条事件编码路径，反降级靠一个检查点保证。
- **需你决定**：是否接受「同一 `kind` 下明文/密文共存」。风险是审计时需依赖状态机判断；若你偏好「靠构造消除明文路径」，我改为新增 `kind=4` 并在产品构建中编掉旧事件 `kind`。
- **若不批**：改 `kind=4` 方案（工作量 +1～2 天）或 PBR2 整帧重设计（不推荐，两端全改）。

### DR-03 身份分层与密钥角色划分

- **我的提案**（对应 f-day1:55 的 key separation）：
  | 角色 | 载体 | 用途 |
  |---|---|---|
  | issuer | Ed25519 私钥（仅 F 的签发环境） | 签发桥板/模块测试身份 |
  | 桥板身份 | Ed25519 密钥对 + `bridge_id` + `key_id`(=公钥指纹) | 双向认证的**身份**，不用于加密 |
  | PBR 会话密钥 | X25519 临时密钥经 ECDH 派生 | **仅** PBR 双向 AEAD，每次会话新生成 |
  | TLS 传输密钥 | TLS 握手派生 | 仅业务面 LAN |
  | 业务 session credential | 现有 `CONFIG_APP_PI_DATA_TOKEN` | 仅业务会话，**不作身份** |
  | UID 索引密钥 | 本机独立秘密 + HMAC-SHA256 | UID 索引派生 |
- **需你决定**：Ed25519 身份密钥是否允许**由 issuer 签发的裸公钥 + 指纹**承载（而非 X.509）；以及 `key_id` 一律取公钥指纹 SHA-256 前 8 字节是否可接受。
- **若不批**：桥板身份改 X.509，Pi 侧需建 CA 与轮换流程（P1 提前到 P0）。

### DR-04 会话密钥派生

- **我的提案**：`ECDH(X25519)` → `HKDF-SHA256(salt=transcript_hash, ikm=shared_secret, info="pbr-secure-v1" || direction)` → 64B 输出 → 拆 `K_i2b[32]` / `K_b2i[32]`；方向密钥**从不重用**，重连即重协商。
- **需你决定**：是否要求 ECDH 静态-临时分离（即桥板用静态 X25519 还是每次临时生成）。临时生成前向保密更好，但需要桥板在重启后仍能证明身份 —— 我倾向「身份密钥签 transcript，会话密钥临时」。
- **若不批**：改为静态 X25519 + 定期重协商。

### DR-05 nonce 与 AAD 构成

- **我的提案**：
  - `nonce = session_id(4) || seq(8) || 0(1)`（12B），`seq` 为会话内**认证序号**（与 `event_id` 分离，符合 f-day1「重传同一逻辑事件使用新的认证序号/nonce」）。
  - `AAD = env_ver(1) || key_id(1) || kind(1) || dir(1) || u32le(auth_seq) || u16le(plaintext_len)`。
  - 序号到 2³²−1 时**强制重新认证**，不环绕复用。
- **需你决定**：AAD 是否必须包含 `boot_id` / `session_id`（我倾向放在 transcript 而非每帧 AAD，避免每帧开销）。

### DR-06 未认证期允许帧集合（**对现状的整改**）

- **问题**：现状 `main.c:124-170` 对 `ping`/`status` 无鉴权，与 f-day1「认证前 ping/status 仅在隔离基线测试中允许，产品安全路径只放行握手」冲突，是一条现成的明文通道。
- **我的提案**：产品构建下，未认证期**只接受** `hello`（握手第 1 条）与 `hello_ack`；`ping`/`status` 仅在 `PBR_ISOLATION_BASELINE=1` 的测试构建中可用，用编译期开关而非运行时判断。
- **需你决定**：是否要求 `ping`/`status` 在认证后也必须走加密（我倾向：认证后全部加密，无例外）。

### DR-07 T-12 设备认证模型

- **我的提案**：**自签证书 + 指纹白名单（pinning）**。TLS ≥1.2，Pi 侧按已配对指纹校验证书；设备身份仍由应用层 Ed25519 签名承担；`TLS 会话 ≠ 设备已认证`。
- **理由**：f-day1:136 明确允许「DIY 自签仅允许显式配对的指纹」；P0 两个 DIY 模块最省事。
- **需你决定**：指纹白名单存放位置（我建议 `QSettings` + Pi profile 双写，便于撤销）以及**撤销后是否必须立即断连**。
- **若不批**：改 mTLS，需 Pi 侧建 CA（P1 提前）。

### DR-08 无硬件期的证据等级（**涉 PR 门禁第 5 条**）

- **我的提案**：把桥板固件 C 代码用 stub HAL 编到 Linux 主机运行（沿用现有 `run_host_tests.py` 思路），两仓跑**同一组**十六进制向量；所有实机相关结论一律标 `NOT_RUN`，不得标 PASS。
- **需你决定**：这类证据在 PR 中算「开发期证据」还是「不可作为合并依据」。**请明确它的效力边界** —— 我不希望因这条被判为「以主机模拟冒充实机验收」。
- **若不批**：我只能在硬件到位后才提 PR，T-03/T-07 会整体顺延。

### DR-09 契约归属与威胁模型联署方式

- **我的提案**：
  - `pbr-secure-v1` 规范**单源**放 Pi 仓 `docs/pbr-secure-v1/`；ESP 仓只写 commit + 路径 + SHA256 引用（避免现有 `sync_module_devkit.py --check` 那类双份漂移）。
  - 威胁模型**与 F 联署**，我只写 **PBR / 事件链路分册**（串口监听、重放、降级、桥板伪造、槽位冲突、迟到事件），交你汇总进全局威胁模型；不覆盖用户/PIN/SQLCipher/worker/网络（那是 Z 与你）。
- **需你决定**：接受「单源 + 引用」还是要求两仓各存一份并交叉校验；以及联署的实际操作方式（我出 90% 草稿你逐条签，还是你先定攻击者能力清单我再写）。
- **若不批**：契约改放 ESP 仓或独立位置，联署改为 F 全写、我只提交输入。

### DR-10 Pi（主机）身份与配对机制（**f-day1 缺口**）

- **问题**：f-day1 只定义了 `bridge_id` / `device_id`，**没有定义 Pi 自己的身份**。而 DR-03 与 f-day1 都写「双向认证」——桥板要认证 Pi，就必须先知道 Pi 是什么。此缺口不补，规范写不下去。
- **我的提案**：Pi 自生成静态 Ed25519 身份（`host_id` + 公钥），**公钥在首次配对时写入桥板 NVS**；此后每次握手，桥板要求 Pi 用该私钥对 transcript 签名。
- **需你决定（关键）**：配对必须配一个**带外授权窗口**（长按 BOOT / 上电后 N 秒内可用）。否则任何插上来的 Pi 都能把公钥写进 NVS，认证等于没有。**这是 f-day1 之外新增的物理动作，请确认可否接受。**
- **已知代价**：换桥板、Pi 重装、NVS 被擦都会触发重新配对并弹窗确认；TOFU 的固有弱点是用户会被训练成"点信任"；Pi 私钥丢失目前**没有恢复路径**，建议列 P1。
- **若不批的回退**：改由 issuer 签发 host 身份（信任根与桥板一致，代价是 F 的签发环境需要多签一份身份，Pi 换机时重新申请）。

### DR-11 四层安全属性的职责划分（含 CRC16 去留）

- **我的提案**：保留帧尾 CRC16，并明确四层各管什么，避免"哪层保证了什么"被追问：

  | 层 | 保证什么 | 明确**不**保证 |
  |---|---|---|
  | CRC16 | 传输误码检测、噪声重同步 | 完整性、认证（对攻击者无效） |
  | 桥板身份 Ed25519 签名 | 桥板身份真实（由 issuer 签发） | 会话机密性 |
  | AEAD tag（ChaCha20-Poly1305） | 报文完整性 + 机密性 + 重放拒绝 | 对端身份（由身份签名负责） |
  | Pi 静态公钥（存于桥板 NVS） | 对端（Pi）身份 | — |

- **需你决定**：是否认可「保留 CRC16，但一律表述为仅检错、绝不称其为 MAC」。DR-02 的信封方案依赖这一条。

### DR-12 协议版本硬切 + 只读诊断通道的边界

- **我的提案**：`hello` 携带 `proto_ver`；不匹配即拒绝并回明确版本错误，升级必须两端同时。为避免现场排障失明，**仅允许一条未加密的 `bridge_status`**，且严格限定内容为：协议版本、桥板 `bridge_id`、固件版本、计数器（不含 UID、不含业务载荷、不可写）。
- **需你决定**：这条诊断通道是否构成「降级」。我建议做到「靠构造排除降级」：产品构建用编译期开关关闭，诊断构建单独出包，并在文档注明二者不同源。
- **若不批**：纯硬切，无诊断通道；排障只能靠日志与串口裸抓。

### DR-13 私钥存储介质

- **我的提案**：桥板身份私钥与 Pi 静态私钥在 P0 均存 **NVS 明文**，文档与代码注释明确标注「**仅测试级，不构成生产保障**」；P1 才上 NVS 加密（eFuse key）或 eFuse 直存。
- **理由**：T-03 要求身份可撤销、可重配；eFuse 直存不可导出、不可轮换，与撤销/重配直接冲突。
- **需你决定**：是否接受 P0 的 NVS 明文测试级，并把 NVS 加密明确列 P1（而不是含糊带过）。

### DR-14 UID 索引密钥归属

- **我的提案**：密钥的生成/存储/轮换归 **Z**（T-04 / T-10 可信存储域）；**D 只实现 `deriveUidIndex(uid)` 与调用点**，不持有该密钥，也不参与其生命周期。
- **理由**：f-day1:58 只写"Pi 用独立本机秘密经 HMAC-SHA256 派生"，没说归谁；T-08 是 D/Z 共主责，不分清就会互相等。
- **需你决定**：确认这个切分；并建议 `deriveUidIndex` 的接口签名在 T-01 由你冻结，避免两侧实现漂移。

### 6.2 F 二次裁决：身份签名算法改用 ECDSA P-256（2026-10-27）

**触发事实**（已在 ESP-IDF 5.5.4 与 Qt 6.5.3 上实地核对）：

| 原语 | ESP-IDF 5.5.4（mbedtls 3.6.5） | Qt 6.5.3 |
|---|---|---|
| `MBEDTLS_ECDH_C` | 存在，Kconfig `default y` | 无裸 ECDH API |
| `MBEDTLS_ECP_DP_CURVE25519_ENABLED` | 存在，`default y` | 无 |
| `MBEDTLS_CHACHAPOLY_C` | 存在，Kconfig **`default n`** | 无 |
| `MBEDTLS_HKDF_C` | 存在，Kconfig **`default n`** | 无 |
| Ed25519 | **仅 PSA 层有 `PSA_ALG_PURE_EDDSA`**，经典 API 无 `eddsa.h`/`ed25519.h` | 无 |
| ECDSA P-256 | `MBEDTLS_ECDSA_C` 存在，`default y` | `QSslKey` 可加载但无签名 API |

**裁决**：DR-03 的签名算法由 **Ed25519 改为 ECDSA P-256**。其余分层（issuer / 桥板身份 / PBR 会话密钥 / TLS 传输密钥 / session credential / UID 索引密钥）不变。

**理由**：一套 mbedtls 两端通用（Pi 侧 libmbedtls 2.28 亦有 ECDSA P-256），X25519 会话密钥交换、HKDF、ChaCha20-Poly1305 全部原生支持；只动签名算法这一项，远小于“每端引入一个额外库、Pi 还要手搓 HKDF”。

**随之变更**：

- `key_id` 仍为公钥 SHA-256 前 8 字节，但公钥编码长度为 65 字节（未压缩点），不再是 32 字节。
- ESP 侧必须在 `sdkconfig.defaults` 显式打开 `CONFIG_MBEDTLS_CHACHAPOLY_C` 与 `CONFIG_MBEDTLS_HKDF_C`（两者默认关闭）；已实测打开后固件可编。
- Pi 侧新增 mbedtls 开发头文件依赖，按 `docs/native-runtime-modules.md` 的依赖清单以 `apt download libmbedtls-dev` 解包方式供应，不 vendored、不要求 `sudo apt install`。

**仍未解决**：DR-02/03/05 对 `key_id` 宽度的描述互相矛盾（1 字节 / 8 字节 / JSON 字符串 1～64 字符），已在 `pbr-secure-v1.md` §2.1 唯一定义（线上 1 字节选钥 + JSON 2 位 hex + TrustStore 用完整公钥指纹），D 的决议文件仍保留原文，由 follow-up 统一。

### 6.9 自查发现的三处自身错误（F 更正，2026-10-27）

我在交付 §6.4 的规范后重新自查，发现规范与向量本身有 3 个错误，均已修正：

1. **`msg3_body` 把签名算进 transcript，构成自引用。** 原写 `msg3_body = key_id || pub || signature`，而 `signature = sign(T)`，`T` 又包含 `msg3_body`，逻辑上不可实现。已改为 `msg3_body = key_id || pub`（66 字节，参与 T），`sig` 单独随命令发送、不参与 T。向量里 `msg3_body` 实测就是 66 字节，反而证明原规范文字与向量不一致。
2. **信封用了错误的方向密钥。** 向量明文是 `attach`（桥板→Pi，`dir=1`），但加密用的是 `k_pi_to_bridge`。已改为 `k_bridge_to_pi`；AAD 的 `dir` 字节本来就是 1，两处现在一致。用错方向的实现会"通过向量但方向反了"，属于抓不住的错误。
3. **签名不可重现。** ECDSA 的 `k` 随机，`gen_vectors.py` 每次重跑都产生不同签名，违反"向量可复现"这一条。已改为：已存在且验签通过时复用，仅在缺失/校验失败时新生成。现在连续两次生成完全一致。

**教训**：§6.4 里我说"自检已过"，但那次自检只验了"能解密"，没验"用什么密钥解密才对"、也没验"重跑是否一致"。**解密成功不等于方向正确。**

**仍然成立**：`hello_finish` 的 JSON 实测 329 字节（不是先前估的 290），256 上限必然丢弃，512 有 183 字节余量。上限改 512 的裁决不变。

证明 ping/status 应答确实被编译期移除，不是运行时判断。两种配置均编过，分区余量 47%。改动在本地 ESP 克隆，**未推送**。

### 6.11 自查补充：拒绝顺序里的未认证 DoS（重要）

原规范第 6.2 节的顺序是先验 `auth_seq` 单调性、后验 tag。这是个可利用的未认证 DoS：攻击者不持有任何密钥，只需发一条 `auth_seq = 2^63` 的伪造帧，接收方就会把序号窗口推高，随后所有合法帧被判 `REPLAY` 并触发重握手。

**更正**：tag 必须在 `auth_seq` 之前验。序号只有在 tag 通过后才可信。同时补明 `IDENTITY_REJECTED` 与 `UNSUPPORTED_VERSION` 的可见性——信封内的失败一律不回应，只入本地审计；只有明文 `hello` 阶段与已认证会话内才回错误帧。
